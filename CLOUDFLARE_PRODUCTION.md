# Cloudflare production deployment — yasirzayed.com

## 1. What this doc covers
Production configuration for the Yasir Zayed site when it runs on Cloudflare Workers.
It is not a how-to for other hosts. It is the canonical note for the production
Cloudflare project only.

## 2. Production origin
- Canonical production host: `https://yasirzayed.com`
- `www.yasirzayed.com` is folded into the apex.
- There is no production `*.workers.dev` endpoint and no Freebuff preview host involved
  in the live production responses.

## 3. Deploy/update path
Development and update pushing go through Freebuff only.

- Development: Freebuff-hosted preview environment.
- Updating production: Freebuff Cloudflare publish flow (sites deploy), then smoke-test
  against `https://yasirzayed.com`.

Do not treat `workers.dev` or any Freebuff preview URL as a production target. The
production responses must not expose or redirect to them.

## 4. What the repo already enforces
- `wrangler.jsonc`: `workers_dev` is `false`; routes are bound to `yasirzayed.com` and
  `www.yasirzayed.com` only.
- `worker.js`: written responses (the HTTP→HTTPS redirect, the `www`→apex redirect, and
  both 404 variants) pin HSTS. The static-asset layer supplies HSTS for served pages and
  assets via `public/_headers`.
- `public/_headers`: sets HSTS, security, and caching headers for the production domain.
- `src/lib/backend.ts`: production Convex URL is the safe default; dev-only env files are
  ignored by `.gitignore`, so a shipped build cannot silently point at a dev backend.
- `public/robots.txt` and `public/sitemap.xml` are generated/written for the production
  origin `https://yasirzayed.com`.

## 6. If a request shows a `502 Bad Gateway` page signed by nginx

That page cannot be produced by this deployment. A `502` whose body ends in
`<center>nginx</center>` is generated by an nginx reverse proxy whose upstream
(php-fpm, Node, Passenger, uwsgi) is down - and no nginx sits in front of this domain.

It means the browser is not reaching Cloudflare for that request:

1. Check what the machine resolves: `nslookup yasirzayed.com`. The only valid answers are
   `104.21.87.229` / `172.67.147.205`, plus `2606:4700:3032::6815:57e5` /
   `2606:4700:3033::ac43:93cd` for IPv6. Anything else is a stale record from the
   previous host.
2. Flush resolver and browser caches: `ipconfig /flushdns` (Windows),
   `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder` (macOS),
   `sudo resolvectl flush-caches` (Linux), `chrome://net-internals/#dns` -> Clear host
   cache.
3. If the stale answer persists, the ISP resolver is still serving the old host: use
   `1.1.1.1` on the machine or test from mobile data.
4. If the old nginx box still exists with a vhost for this domain, stop or delete that
   vhost. Until it is gone, anyone whose DNS points at it keeps seeing its 502.

Apex and `www` have no non-Cloudflare addresses, so this is a client-side resolution
problem (or a retired origin still running), never a missing deploy.

## 7. If a deploy is blocked
If a future deploy cannot complete, the usual blockers are:
- Missing Cloudflare Workers deploy auth for the production zone/account.
- Missing production Convex URL in the deploy environment for the build step.

Do not paste or commit real secret values. If one is required to finish a deploy, say
which one is missing and where it must be set, then stop until it is provided.

## 9. Serving `dist/` from nginx (alternative host)

`_headers` is consumed by Cloudflare's asset layer only. On an nginx host every rule in it
has to live in the server block instead. The block below is the tested equivalent of the
production behaviour: one-hop HTTP→HTTPS, `www`→apex, HSTS on every response, hashed
assets cached for a year, HTML revalidated, and SPA routes falling back to `index.html`.

Replace the `root` and certificate paths, then include it from the `http` block. It was
verified with nginx 1.31.10 using a locally generated self-signed certificate.

```nginx
server {                                   # port 80 -> HTTPS, one hop
  listen 80; listen [::]:80;
  server_name yasirzayed.com www.yasirzayed.com;
  return 301 https://yasirzayed.com$request_uri;
}

server {
  listen 443 ssl http2; listen [::]:443 ssl http2;
  server_name www.yasirzayed.com;
  return 301 https://yasirzayed.com$request_uri;

  ssl_certificate     /etc/letsencrypt/live/yasirzayed.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/yasirzayed.com/privkey.pem;

  add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
}

server {
  listen 443 ssl http2; listen [::]:443 ssl http2;
  server_name yasirzayed.com;
  root /var/www/yasirzayed/dist;
  index index.html;

  ssl_certificate     /etc/letsencrypt/live/yasirzayed.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/yasirzayed.com/privkey.pem;

  add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
  add_header X-Content-Type-Options nosniff always;
  add_header Referrer-Policy strict-origin-when-cross-origin always;
  add_header X-Frame-Options SAMEORIGIN always;

  expires -1;                              # HTML: Cache-Control: no-cache

  location /assets/ { try_files $uri =404; expires 1y; }
  location / { try_files $uri $uri/ /index.html; }
}
```

Notes that matter if this block is edited:

- Do **not** put `add_header` inside a `location`. nginx drops every inherited
  `add_header` as soon as a nested block declares one, and `try_files ... /index.html`
  sends every SPA route through the `/index.html` location — the original handover used
  `add_header Cache-Control` in two nested blocks and lost HSTS on the whole site.
  `expires -1` / `expires 1y` set caching without touching header inheritance.
- `expires 1y` on `/assets/` yields `Cache-Control: max-age=31536000`; it is not
  `immutable`, because adding that needs `add_header` and would re-break inheritance.
- `listen 443 ssl http2` is correct for nginx 1.24 (Ubuntu 24.04). nginx 1.25.1+ logs a
  deprecation warning and prefers `listen 443 ssl;` plus `http2 on;`.
- `sitemap.xml` and `robots.txt` are served as ordinary static files. `_headers` is inert
  on nginx (nothing reads it) but would be downloadable at `/_headers`; delete it from the
  upload, or add `location = /_headers { return 404; }` if you leave it in place.
